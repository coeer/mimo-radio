## 案例 1：评严重度前先 grep 读取方——"写多读少"的状态未必是 bug

**背景**：cross-review 时 KIMI 发现 `pendingResume`（useSession.ts:28 注释承诺消费）全前端零读取方，直觉判 🔴"死状态"。但进一步推演发现它是 R3 挂起语义的观测标记，ZCode 原 review 把 prevSong source='user' 判 🔴"双音轨"，KIMI 复核后降级——因为 UI 假 On Air 而非真双音轨。

**教训**：一个状态/字段"没人读"不等于"可以删"也不等于"严重 bug"。评严重度前先 grep 全部读取方 + 推演它的隐式消费者（测试断言、日志、未来契约），再定档。本轮 7🔴→4🔴 的校准有 3 项来自这个动作。

**建议条款**：评审发现涉及"状态/字段死活"时，必须附 `grep -r` 读取方证据进报告，无证据的 🔴 降级为 🟡 待证。

## 案例 2：判"弱断言/假绿"前做变异推演——测试绿也可能照样错

**背景**：KIMI 推翻 ZCode 的 R-5 场景 3 判定时，用的是变异推演法：把 R2 transition 锁从源码里删掉，重跑测试——如果测试还绿，说明断言根本没锁住该规则（假绿）。本轮场景 3 被判"弱断言"后 KIMI 实际验证：删 R2 后测试**变红**，证明断言有效，ZCode 原判不成立。

**教训**：判一个测试"弱断言"不能只读断言文本，要做变异推演（mutation reasoning）：假想删掉被测规则，断言会红吗？会红=有效；还绿=假绿。反之，写测试时也应自问"这条断言能抓住哪个变异"——N-5（R2 先于 R3 顺序锁定）就是按这个思路补的。

**建议条款**：评审判"弱断言/假绿"时必须写出变异推演过程（删什么 → 断言红/绿）；新增测试在注释里写明它锁死的规则。

## 案例 3：高复杂度并发模块用双盲交叉验证——单评审者的场景推演必有盲区

**背景**：F4 仲裁层（playRequest R1-R5 + nextSong 两阶段）是本轮分歧最集中的模块：ZCode 7🔴 中 3 项（R-3/R-4/R-5）经 KIMI 独立复核后降级或撤销，KIMI 又补出 ZCode 漏的 N-1（阶段 2 死路径，本轮最高价值发现）。同一模块两份 review 交集很小——不是谁水平问题，是并发状态机的场景空间超出单人穷举能力。

**教训**：对"多触发源 × 多状态位 × 异步窗口"的模块（仲裁层、熔断器、队列调度），单一评审者的场景推演必然有盲区。双盲交叉验证（双方独立推演同一矩阵再对比）的边际收益远大于普通模块。本轮 §1.2 的 11 场景矩阵就是合并双方推演后的产物，比任何一方单独的版本都完整。

**建议条款**：模块满足"≥3 个并发触发源 且 ≥2 个互斥状态位"时，评审报告必须附场景矩阵（触发源 × 状态 → 终态），且该类模块的 review 结论需第二人独立复核方可定档 🔴。
